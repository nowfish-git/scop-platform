2. 需求背景

2.1 行业背景

中国正处于深度老龄化社会加速期。截至2025年底，全国60岁及以上老年人口已达3.2亿，占总人口的22.8%。国家推行"9073"养老格局——90%居家养老、7%社区养老、3%机构养老，居家社区养老是绝对主战场。

政策层面，"十四五"国家老龄事业发展和养老服务体系规划明确提出：推动智慧健康养老产业发展，建设基本养老服务综合平台，推进智能产品在养老领域的深度应用。"十五五"规划进一步将智慧养老列为银发经济核心赛道。

技术层面，物联网（IoT）、5G、人工智能、云计算技术的成熟，使低成本、规模化部署智能养老设备成为可能。烟感报警器、门磁传感器、紧急呼叫按钮、智能穿戴设备等硬件成本持续下降，为社区级养老安全监测方案的落地提供了基础条件。

2.2 用户痛点

用户角色 核心痛点
社区家庭老人 独居或空巢时缺乏安全感，突发疾病或摔倒无法及时求助；对智能设备操作不熟练，子女不在身边缺乏照护
社区工作站人员 辖区内老人数量多、分布散，无法实时掌握老人安全状况；工单管理靠纸质或Excel，效率低下；服务派单缺乏系统化工具
平台运营者 缺乏数据驱动的运营决策能力；服务商管理混乱；套餐和订阅管理缺乏统一平台
老人家属/子女 无法实时了解父母健康状况；担心父母发生意外却不知情；缺乏与社区服务联动的渠道
物业 缺乏与服务请求对接的统一渠道，巡检和上门服务依赖人工指派，效率低、过程不可追溯；与社区工作站、服务商协同成本高
服务商 缺乏稳定的订单来源和精准的服务匹配渠道；服务过程缺乏数据沉淀，难以形成口碑和复购；结算与对账分散在多个线下流程

2.3 市场机会

  • 市场规模：2025年中国智慧养老市场规模约5000亿元人民币，年复合增长率超20%
  • 竞争格局：涂鸦智慧养老偏重IoT平台能力，蓝色健康覆盖全场景但以机构养老为主，社村通侧重系统平台建设——在"社区级居家安全+健康监测+家属联动"这一细分组合上，仍有差异化机会
  • 差异化切入点：以订阅制商业模式降低用户门槛，硬件+平台+服务一体化交付，强调家属端的远程关怀能力；并以家庭为单元建立数字化运营体系（FDOS），形成可持续运营的社区生活服务基础设施

3. 产品定位与架构

3.1 产品命名

SCOP（Smart Community Operation Platform）智慧社区运营平台。

3.2 产品定位

以家庭为服务单元，以老年群体为核心用户，以订阅式社区生活服务为商业模式，以 AI 和 IoT 为技术底座，构建可持续运营的智慧社区服务生态。

SCOP 不是传统智慧社区软件，而是社区生活服务基础设施：通过家庭数字化运营 + AI + IoT 构建持续增长的社区生态系统，连接居民家庭、社区工作站、物业及服务商，提供订阅式社区生活服务。

3.3 核心转型目标

实现社区从"建设型智慧社区"向"运营型社区服务平台"转型，建立以家庭为中心的数字化运营体系（FDOS，Family Digital Operation System），形成"感知 → 告警 → 服务 → 评价 → 沉淀"的持续服务闭环。

3.4 五端体系

家庭中心 家庭档案、成员关系、订阅管理

4. 产品目标

4.1 业务目标

  • 第一年目标：签约不少于20个社区，覆盖不少于2000户老人家庭，月活跃用户留存率 ≥ 85%
  • 订阅收入目标：首年实现月度经常性收入（MRR）突破100万元
  • 告警响应时效：紧急告警的平均响应时间 ≤ 3分钟（从触发到工作站人员确认）

4.2 用户目标

用户角色 核心目标
社区老人 居家安全有保障，紧急情况能快速获得帮助，健康状况可被关注
社区工作站 高效管理辖区内老人，快速响应告警，工单流转可追溯
平台运营者 数据可视化运营，服务商统一管理，套餐灵活配置
老人家属 远程查看父母健康与安全状态，接收实时告警通知
物业 高效执行社区服务指令，降低人工巡检成本
服务商 获得稳定订单来源，提升服务效率和收入

4.3 第一阶段目标（V1.0）

聚焦 居家安全 + 健康监测 两大核心板块：

  • 居家安全：烟感告警、门磁异常、紧急按钮SOS、智能穿戴设备告警的全链路闭环
  • 健康监测：血压、心率、血氧、睡眠等健康数据的采集、展示与异常告警
  • 用户端：老人端小程序（极简模式）+ 家属端小程序
  • 工作站端：Web后台，含告警处理、工单管理、老人档案管理
  • 运营后台：平台配置、服务商管理、套餐管理、数据看板

8.1 居家安全模块

8.1.1 设备管理

F-001 设备注册与绑定

属性 内容
优先级 P0
用户角色 安装人员、工作站人员

EARS 需求描述：

  • 通用性 系统应支持烟感报警器、门磁传感器、紧急呼叫按钮、智能穿戴手环四种设备类型的注册。
  • 事件驱动 当安装人员使用工作站端扫描设备二维码时，系统应自动识别设备类型并进入设备绑定流程。
  • 状态驱动 在设备绑定流程未完成的情况下，系统应阻止该设备上报数据进入正式告警通道，所有上报数据标记为"测试模式"。
  • 事件驱动 当设备绑定成功时，系统应将设备状态设置为"在线"，并将设备与指定老人档案自动关联。
  • 异常行为 如果扫描的二维码已被其他老人绑定，那么系统应提示"设备已被绑定，请先解绑"，并阻止重复绑定。
  • 异常行为 如果设备在绑定后30分钟内未上报任何数据，那么系统应将该设备标记为"待确认"状态，并向工作站发送确认提醒。

交互边界： - 一个老人可绑定多个设备（最多：烟感2个、门磁3个、紧急按钮3个、穿戴设备1个） - 一个设备同一时间只能绑定一位老人 - 设备解绑需要工作站人员权限，解绑后设备数据保留30天

异常场景： | 场景 | 处理方式 | |------|----------| | 扫码时网络断开 | 提示"网络异常，请检查网络连接后重试"，支持离线缓存，网络恢复后自动提交 | | 设备类型无法识别 | 提示"无法识别设备类型，请确认二维码是否正确"，并记录异常日志 | | 绑定过程中设备断电 | 绑定流程暂停，设备恢复供电后自动继续绑定流程 |

8.1.2 告警中心

F-004 告警规则引擎

属性 内容
优先级 P0
用户角色 系统自动、运营后台配置

EARS 需求描述：

  • 通用性 告警规则引擎应支持按设备类型、告警等级、生效时间段三个维度配置告警规则。
  • 事件驱动 当IoT平台接收到设备上报的告警信号时，告警规则引擎应在500毫秒内完成规则匹配并生成告警记录。
  • 状态驱动 在告警规则被运营后台禁用的情况下，该规则不应触发任何告警通知。
  • 可选特性 在启用告警静默时段功能的条件下，在静默时段（如22:00-06:00）内，P2-一般告警应仅记录不推送通知，P0/P1告警应正常推送。
  • 异常行为 如果同一设备在5分钟内重复上报相同类型的告警信号，那么系统应合并为一条告警记录，并在告警详情中记录重复次数。
  • 异常行为 如果告警规则引擎服务不可用，那么系统应将所有收到的告警信号暂存至消息队列，待服务恢复后逐条处理。

告警等级定义：

等级 标识 颜色 典型场景 通知方式
P0-紧急 CRITICAL 红色 紧急按钮按下、烟感触发、穿戴设备SOS 工作站弹窗+声音+短信、家属微信+短信
P1-重要 MAJOR 橙色 门磁深夜异常开启、健康指标严重异常 工作站弹窗、家属微信通知
P2-一般 MINOR 黄色 设备离线超过1小时、设备低电量、健康轻度异常 工作站消息列表、家属微信通知

F-005 告警处理闭环

属性 内容
优先级 P0
用户角色 工作站人员

EARS 需求描述：

  • 事件驱动 当工作站人员确认收到告警时，系统应将告警状态从"待确认"变更为"处理中"，并记录确认人和确认时间。
  • 事件驱动 当工作站人员完成告警处理并提交处理结果时，系统应将告警状态变更为"已完成"，并自动生成回访任务。
  • 事件驱动 当回访任务完成且老人确认问题已解决时，系统应将告警状态变更为"已关闭"。
  • 异常行为 如果P0-紧急告警在3分钟内未被任何工作站人员确认，那么系统应自动将告警升级，通知工作站主管，并再次推送告警。
  • 异常行为 如果P0-紧急告警在5分钟内未被确认，那么系统应通知平台运营人员，并自动拨打预设的紧急联系人电话。
  • 状态驱动 在告警状态为"已关闭"的情况下，系统应禁止对该告警进行任何修改操作。

告警处理状态机：

待确认 ──(确认)──> 处理中 ──(完成)──> 待回访 ──(回访确认)──> 已关闭
   │                  │                    │
   └──(超时升级)──────┘                    └──(回访异常)──> 处理中（重新处理）

8.6 紧急救援联动（新增）

F-112 紧急救援联动

属性 内容
优先级 P1
用户角色 系统自动、社区工作站、社区医院、120 急救、家属

功能说明： 当 P0 紧急告警超时未确认且系统判断可能涉及生命安全时，自动启动紧急救援联动流程，将告警升级为救援事件，多通道通知社区医院、120 急救中心、家属，并全程追踪救援过程。

EARS 需求描述：

  • 事件驱动 当 P0-紧急告警在 5 分钟内未被工作站确认，且系统判断可能涉及生命安全时，系统应自动启动紧急救援联动流程，通知社区医院和 120 急救中心。
  • 事件驱动 当紧急救援联动启动时，系统应同时向家属推送救援通知，包含老人位置、健康状况摘要和已通知的救援方。
  • 异常行为 如果社区医院联系方式未配置或不可达，系统应跳过医院通知直接联系 120 急救中心。
  • 状态驱动 在救援联动已启动且未关闭的情况下，工作站告警详情面板应置顶展示救援进度时间线，并禁用"关闭告警"操作，仅允许"救援完成"或"误报取消"两种结束操作。
  • 异常行为 如果 120 急救通知通道调用失败，系统应自动重试 3 次（间隔 30 秒），仍失败时降级为电话语音播报并通知平台运营人员介入。
  • 通用性 救援联动全程关键节点（启动、医院通知、120 通知、家属通知、抵达、完成）均应记入救援事件时间线，并作为救援复盘报告的数据来源。

交互边界： - 救援联动是告警升级流程的延伸，不影响原有 P0 告警的弹窗、声音、短信通知逻辑 - 救援事件与原告警通过 alert_id 关联，一个告警最多生成一个救援事件 - 救援事件关闭后，原告警自动流转为"已关闭"，并在告警详情中标注"经救援联动关闭"

SEC-01 所有API接口必须使用HTTPS加密传输
SEC-02 用户密码存储必须使用bcrypt或等效算法加密，禁止明文存储
SEC-03 敏感数据（老人身份证号、联系电话、健康数据）在数据库中必须加密存储
SEC-04 接口调用必须进行身份认证（JWT Token），Token有效期不超过24小时
SEC-05 操作日志必须记录所有敏感操作（查看/修改老人档案、处理告警、修改套餐），日志不可删除
SEC-06 数据权限隔离：工作站人员仅可查看本社区数据，家属仅可查看绑定老人的数据
SEC-07 SQL注入、XSS、CSRF攻击防护
